## 一、我对作者意图的理解

这次整理要解决的是：论文结果已经阶段性确定，但支撑这些结果的文件、代码和说明逐渐分散。以后替换实验条件或增加实验时，作者应当能立即知道某张图读的是哪一次实验的什么结果，怎样重新画出当前版本，以及旧版本何时退出。

整理后的实验追溯只有两个实质环节：

**服务器上可明确定位的原始运行结果 → 本仓库中直接读取该结果的绘图、制表或统计代码。**

主项目仓库解释实验结果怎样产生；论文仓库解释原始结果怎样被选择、统计和展示。handoff 负责把实际命令、实验条件、产物位置和图的使用关系说清楚。它记录这条关系，不成为另一个数据来源。

本地不再长期保存一套供绘图入口优先读取的实验结果，不再依靠 `talk/` 的行动日志拼接来源，也不再以“与服务器相同”为理由保留第二套长期科学输入。共享读取和统计实现可以保留，但每张当前图必须有明确、独立的绘图入口；作者修改后的版本也一样。

本次整理以提交 `13ccc034a738ff1474c12496eac4f4fb6100f874` 中的 `draft.nature.docx` 和 `supplementary.nature.docx` 为不可改动的论文基线。整理代码和来源时，不能以改进版式、更新数据或修正文句为由替换这两份 Word。对于基线中已经查出的事实或表述冲突，应当如实报告，并由作者另行决定是否修稿。

作者关于已通过内部初审、未来可能再发生两至三轮大改的说明，作为本计划的工作背景；它们不是由仓库文件能够独立证明的实验结论。计划据此保证新实验条件可以独立接入，旧论文仍可复现。

## 四、拟采用的最短工作方式

### 1. 服务器保留一次实验的原始结果

每次实验有明确的 `/storage` 产物根目录。新条件或重做实验使用新根，不覆盖被冻结论文采用的旧结果。论文绘图代码明确选择实际实验根、受体、模型、阈值、集合和原候选排序，不按目录修改时间选择“最新结果”，也不自动用另一条件补缺。

模型、数据准备、推理和评价的长期实现归属对应主仓库。现有仍散在服务器 `tmp/`、任务专用根或本地 `output/` 的必要程序，需要在保留实际历史事实的前提下整理进主仓库正式实现和命令入口。不能把主仓库当前 HEAD 说成历史实验当时实际运行的 release。

旧实验已经怎样运行，与今后可以怎样重建，必须在同一 handoff 中分别写明。整理后建立的正式命令不能倒填成旧实验当年调用过的命令。

### 2. 本地每张图有独立入口，直接选择服务器结果

保留当前 `stage1/stage2/stage3/e2e` 的阶段组织，以及有实际阅读价值的计算／可视化区分。每张采用中的图在所属位置拥有独立目录或函数。作者版与原版平行，例如：

```text
画图/画图代码/stage1/calculate/
├─ stage1-overall-performance/       # 基础图；若退场，由共享统计实现替代其依赖
└─ stage1-overall-performance-v1/    # 当前作者版，独立定义显示和完整重建入口
```

路径中的 `-v1` 与 PPT 中完整 `@@stage1-overall-performance(v1)` 明确对应，不通过剥离后缀自动继承。共有的科学计算放在已有的共享模块中，不复制评价定义，也不为形式整齐增加多层转发。

每个入口连续、清楚地完成：读取指定服务器结果、按已定义统计条件取数、生成图形、应用该图的版式、装配可编辑 PPT 和图注。所有新生成文件写入本次 `temp/` 构建目录。

总览中的 geraniol、ibuprofen、naproxen 示意构象、合成密度和流程形状属于展示设计，由本地正式构造代码、固定随机种子和明确设计参数生成，不冒称服务器模型的实验结果。真实实验材料仍按服务器原件读取。提取作者 PPT 时，只提取版式、文字、连线、颜色和显示变换；不能把旧性能曲线路径、原子坐标或密度网格硬编码进代码，伪装成从服务器重新绘制。

最终入口不得把旧 `补充数据/`、旧 `output/`、`archive/`、作者 CXS 中的坐标数组或 D 盘结果镜像作为科学数据的替代读取位置。服务器不可读或指定文件不存在时，直接报告具体文件；不能静默切回本地旧副本。

### 3. 关于“直接读取服务器”的具体含义，请作者确认

我建议允许一次绘图运行在 `temp/` 内接收服务器文件，供需要本地路径的 ChimeraX、PowerPoint 配套步骤使用。这个目录没有人工编辑入口，不能被后续运行复用，删除后必须重新从同一个服务器路径读取。JSON／JSONL 等可以直接流式读取的输入，尽量在内存中处理。

这项建议涉及你对“极短追溯链”的边界，不能代你决定。如果你要求连这种单次运行的磁盘暂存也完全禁止，就要为原生三维工具提供只读远程文件访问或改写加载接口；当前仓库没有已经建成、覆盖所有原生绘图入口的这类实现。

无论选择哪种访问方式，都不设置长期本地数据镜像，不形成新的人工维护数据层，也不以缓存内容定义实验事实。

### 4. handoff 的内容和双份规则

每个实验产物根的 `handoff.md`，在本地 `追溯文档/` 下保留同名、可唯一定位的一份副本；本地可用实验名称或运行标识分目录，避免同名覆盖。两份文件按同一份 UTF-8 字节内容同步，统一换行；传输后逐字节比对，不能分别手工维护两份近似文本。

handoff 至少回答：

1. 该次实验回答什么问题，使用什么输入、数据集合、模型、checkpoint 和配置。
2. 历史实际命令是什么，属于哪个仓库、release 和 launch；哪些来自历史临时脚本。
3. 当前正式入口的完整命令是什么，逐个关键参数怎样影响结果，产物写到哪里。
4. 哪些原始文件提供身份、样本成员、排序、RMSD、评价计数或计时，失败如何保留。
5. 当前论文哪些图、表和独立数字使用它，本地具体绘图入口是什么，采用哪个实验条件和作者版本。
6. 当前哪些结果已经退出论文，哪些仅因作者明确选择而继续保留，以及已知的原文事实冲突。

这里不另建人工维护的 JSON 来源数据库、八份活动追溯文档、规划—执行—映射索引或逐日行动日志。必要机器配置只服务实际代码运行，不能独立解释或改写科学事实。

PPT 中继续保留 `@@图名`、作者批注和双语图注。来源批注改为指向对应 handoff、服务器实验根及本地入口的简明指路信息；不再同步一整套容易过时的第二份解释正文。图注仍回到所属 PPT 维护。

额外的实验解释文档只有在作者明确许可、并从 `追溯文档/` 明确链接后才保留。术语表、转换工具接口说明等既有工作规则的取舍单列审核，不把它们自动改造成另一套实验追溯文档。
