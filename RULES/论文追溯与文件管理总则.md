- 计算资源在服务器上。实验的运行、结果记录也都在服务器上。在跑实验或运行结果时，我们把长期代码写在本地然后同步到服务器上并进行运行。
- 写论文时，论文仓库在本地。通过读取服务器上的真值数据画图画表。同时，服务器的根目录 `/home/penghongen/manuscript_full_history/`  下会含有本地论文仓库的备份，用以维持更全面的 git 状态并提供时间上的追溯。
- 下面的规则和要求，如：图表的追溯、Git 的追溯、CXS追溯等，它们会派生出一系列的规则，必须持久遵守，并检查维护。
- 这是论文仓库。写论文时，除非得到作者的明确允许，否则绝不可以反过来修改、移动或删除服务器上的真值数据。



## 图表的层次化追溯原则

论文中的图片由相应的 .md 文档使用 “PPT 路径＋`@@稳定图名`” 的语法来直接(在编译的word里)插入PPT中的某一页，所有 PPT 位于 `画图/PPT/`。当我们说起一张图片时，具体地，链条为：

正文或补充材料中实际出现的图片(或BACKUP图片)————>
对应的实际PPT中的图片，规定实际视觉效果————>
对应的 C:\Users\15919\Desktop\论文草稿\画图\画图代码 里面的某个子文件夹，规定这个图片的实际产生过程————>
图片绘制所需的科学真值必须来源于服务器(即便备份在本地D盘也必须保证D盘的数据与服务器上的对应数据100%相同，而没有任何额外文件或额外处理)。

对于表格也类似，不过表格可能在 .md 中直接展示，所以上面的前2步可能不再适用，不过同样地要在 C:\Users\15919\Desktop\论文草稿\画图\画图代码 里面的某个子文件夹，规定这个表格的实际产生过程。

`画图/` 下面只有 `Chimera/`、`古法Chimera/`、`PPT/`、`画图代码/` 这四个子目录，无其他子目录或者文件。`画图/画图代码/` 只设 `正文/`、`补充材料/`、`BACKUP/`。

对于在正文中、补充材料中出现的图表，以及作为可能启用的备份图，除了作者额外规定的"多图分组"之外，必须全部分别在：
C:\Users\15919\Desktop\论文草稿\画图\画图代码\正文、
C:\Users\15919\Desktop\论文草稿\画图\画图代码\补充材料、
C:\Users\15919\Desktop\论文草稿\画图\画图代码\BACKUP 
下创建一个专属子目录，所有画图表的全部逻辑都要在专属子目录内，且还要额外含有人类可读的 trace.md 以及 README.md 用来提供追溯来源。



具体地，对架构的规定:

- 作者可能认为不同图片来源相似，绘制逻辑也相似，此时，作者会人为地为不同图片特别地指定分组，使它们合并管理并共享一个(C:\Users\15919\Desktop\论文草稿\画图\画图代码下的)子目录。比如，作者会说："当前补充材料中的 Fig6~8，以及 Fig9~10 非常相似，我们可以把它们合并管理，同时使它们在 C:\Users\15919\Desktop\论文草稿\画图\画图代码 下共享追溯子目录"。当然，AI agent 无权自行决定是否合并管理，必须请示作者。对于作者认定的"多图分组"管理，必须记录在本文档的最下方作为显式例外规则。除此之外必须严格地"一图一子目录"。

- 对于 `画图/PPT/BACKUP.pptx` 内的后备图表，仍然默认地采用"一图一子目录"(子目录位于 C:\Users\15919\Desktop\论文草稿\画图\画图代码\BACKUP 内)。


- 原则上，"C:\Users\15919\Desktop\论文草稿\画图\画图代码 里面的子文件夹追溯的所有图表"，必须精确地 
= "正文与补充材料中出现的图表 + `画图/PPT/BACKUP.pptx` 内的后备图表"。
如果前述等式不满足，AI agent 必须立刻确认精细追溯、通知作者并告知可能的修复方案。


- 但注意，上一条实际上容许了一种现象: 作者可能会在相应的某个PPT内对已有的图片进行复制粘贴，意图进行额外编辑，并在完成后作为下一个版本的正文或补充材料中的图片。这种情况下，作者会约定，在这页PPT内以批注的形式明确交代："这页PPT实际上是本PPT内第x页的科学含义不变的前提下的复制粘贴"，这条批注的语言字句有一定自由度；但是，必须同时有一个单独的，精确等于"drafting"的批注。按照此条规则，上一条的等式可以强化至：

    "C:\Users\15919\Desktop\论文草稿\画图\画图代码 里面的子文件夹追溯的所有图表 "，必须精确地 
    = "正文与补充材料中出现的图表 + `画图/PPT/BACKUP.pptx` 内的后备图表" 
    = .md 中直接写的表格(但经过 C:\Users\15919\Desktop\论文草稿\画图\画图代码 的唯一子目录追溯) + "C:\Users\15919\Desktop\论文草稿\画图\PPT" 里面所有 PPT 页对应的所有图表 - 对应页含有精确等于"drafting"的批注的对应PPT页。

## Git 层面的追溯: 本地精选 Git 与服务器全面 Git

- 本地论文仓库的 git 追踪称为精选 Git，只追踪核心逻辑，且由本地的 git ignore 决定内容：重点跟踪代码、规则、说明、PPT 和正式 Word，忽略大文件如 CXS。具体规则，以及服务器上全面 GIt 的具体含义，由[同步说明](C:/Users/15919/Desktop/论文草稿/TOOLS/sync-to-server/README.md)维护并进行可能的更新，本文档只规定负责的大致范围和权限边界。

- 服务器上对应存在和本地论文仓库几乎类似的目录，它在在 `/home/penghongen/manuscript_full_history/` 下(比如，`/home/penghongen/manuscript_full_history/LigandSeek`)。服务器上的目录和本地论文仓库内容上几乎相同，即相当于备份，收录所有非临时实体文件，包括 ignored 文件、CXS、`.review/`、固定依赖及作者素材。但是服务器上的目录使用了更广泛的 Git 追踪：只排除根 `.git/` 和根 `temp/`，所以可以视为更全面的时间线的备份。

- `TOOLS/sync-to-server/` 用以自动化地根据本地论文仓库同步服务器上的对应目录，并构建服务器上的全面 Git 并建立与本地精选 Git 的对应关系。它捕获明确磁盘状态，记录精选 HEAD、分支、未提交状态和同步编号。传输后从全面 Git 独立恢复，逐文件核对并确认删除反映在新镜像，全部成功才发布有效版本，失败保留上次有效版本。

- 不可以对被替换的不完善状态新增长期备份、分支或归档。既有服务器归档、其它 Git 引用及内部对象不因“不要留下痕迹”自动获得删除许可。

### 缓存与临时文件

缓存分为两种，各自都有明确的存放位置和维护规则：

- 一部分是临时代码或探针的缓存，在单次执行任务时，可以放进 "C:\Users\15919\Desktop\论文草稿\temp" 里面。但是除非明确请求作者的明确审批并得到同意，否则任务结束后必须清空 "C:\Users\15919\Desktop\论文草稿\temp" 里面的一切文件。换句话说，正常情况下在任务执行完毕后，"C:\Users\15919\Desktop\论文草稿\temp" 应该全空。
- 一部分是在对服务器上代码的原样拷贝，在 `D:/AdaLigand_Visualization` 中。该目录下只得存放服务器上的涉及到真值的原件，绝不可做任何额外处理，也不能增加服务器上没有的任何文件。同时，也不得整包搬进项目再由全面 Git 间接保留。这个目录不同于上面的 temp/ ，它可以持久缓存。


### CXS 与古法作者资产

这里的 CXS 为 Chimera 会话，它类似于图表：因为一个 CXS 可以导出供文章引用的图片，并与此同时依赖服务器上的真值。
所以，为了不引入另一套复杂的管理策略，我们这样规定，是的 CXS 的管理规则能够自然地融入上述图表的管理规则中：

- 对于 CXS 的存放根目录，要么在 C:\Users\15919\Desktop\论文草稿\画图\古法Chimera，要么在 C:\Users\15919\Desktop\论文草稿\画图\Chimera 。它们的唯一区别是，前者一般是作者手动调整的 CXS，且除非AI agent 明确请求审批并获得通过，否则完全不能进行改动。这两个根目录下，除了 CXS 文件以及它导出的图片之外，就只能剩下解释性的 .md 文档，绝不可将 .py 脚本等生成式逻辑混入其中。

- 对于一个 CXS 会话，我们要求它要么"对应的导出图片在正文/补充材料中被引用"，要么"对应的导出图片在 `画图/PPT/BACKUP.pptx` 中的某页被展示"。

- 所以 CXS 就可以和图片的"一图一追溯子目录代码"一样被追溯了。
(1). 如果一个 CXS 导出的图片，被放入正文或补充材料的某个图中，则在 C:\Users\15919\Desktop\论文草稿\画图\画图代码\正文 和 C:\Users\15919\Desktop\论文草稿\画图\画图代码\补充材料 中相应图的子目录下，使用 python 代码等手段构造初始 CXS 会话：要确保CXS会话的所有原料都是最终来自服务器真值，且是可追溯的；初始构造代码负责科学材料、坐标、模型及初始显示；作者后续手工调整形成的最终 CXS，是正式显示原件。
(2). 使用 trace.md 和 README.md 说明情况。
(3). 如果如果一个 CXS 导出的图片，被放入 `画图/PPT/BACKUP.pptx` 中，则在 C:\Users\15919\Desktop\论文草稿\画图\画图代码\BACKUP 下同样建立一个"针对于这个CXS会话的追溯子目录"即可。

- 建议 CXS 会话尽量"内置"相应的资料。同时 CXS 所依赖的资料不能停留在 temp/ 中。
